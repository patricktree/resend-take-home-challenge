# Map: Email Draft Approval

Labels: wayfinder:map

## Destination

A spec ready to build from for the email-draft approval system described in [spec-input.md](spec-input.md): architecture, domain model, agent and Reviewer interface contracts, how an Approval is bound to a Revision, how each approved Draft is sent exactly once, and the stack on Cloudflare. The map is done when nothing is left to decide before implementation starts.

## Notes

- Domain: an approval gate between Agents that compose emails and a human Reviewer. Vocabulary lives in [GLOSSARY.md](../../GLOSSARY.md); use its terms (Draft, Draft data, Revision, Submission, Pending, Approval, Rejection, Send, Agent, Reviewer, Review UI, Decided) and run the `domain-modeling` skill alongside `grilling`.
- The design must come from this map alone.
- Standing decisions from charting:
  - Deploy target: Cloudflare platform. Concurrency and exactly-once guarantees live in durable storage and Resend idempotency, never in process memory.
  - Agent interface: an HTTP API described by OpenAPI → a generated or typed TypeScript client → an MCP server and a CLI built on that client. Libraries and repo layout follow `~/workspace/cup` (reading it is allowed).
  - Draft data v1: `to` recipients (list), subject, plain-text body. `from` is fixed by configuration. No cc/bcc, reply-to or attachments.
  - A Rejection applies to one Revision and may carry an optional free-text reason; the Agent may revise and resubmit.
  - An approved Draft is closed: no further Revisions, at most one email sent per Draft.
  - A single preconfigured Reviewer identity.
- The spec must contain a **"Demo simplifications"** section. Each entry states a demo shortcut and what a real deployment would do instead (e.g. single preconfigured Reviewer → SSO/IdP with real identities, roles, audit trail; several humans share that identity, so verdicts are not attributed to a person). Further entries so far: `from` comes from configuration (resolved when the Approval is recorded) and is not part of what the Reviewer approves; no observability or alerting (from 14, merging 07's no-alerting entry: v1 has no `observability` block in `wrangler.jsonc` and only bare `console.error` on error paths; a real deployment adds structured log events with `requestId`/`draftId` correlation and a never-log list, Workers Logs and traces with Logpush or OTLP export, metrics, Review UI error reporting, and alerts on DLQ depth, queue backlog age, Sends `QUEUED` for over 10 minutes, `OUTCOME_UNKNOWN` failures, Resend 429s and quota). From 08: an Agent running as the Reviewer's OS user (able to drive their browser or read their files) is not defended against; a real deployment adds per-verdict passkey confirmation and isolates Agents from the Reviewer's OS account. From 09 and 10: a single shared Agent token, so Drafts are not scoped per Agent (a real deployment gives each Agent its own credential, records it as the creator and scopes reads and writes to it). From 10: a single shared Reviewer token pasted into the Review UI and kept in `localStorage` (a real deployment signs Reviewers in through the organisation's IdP via OpenID Connect, with per-person identities, a Reviewer role, an `HttpOnly` cookie session with CSRF and origin checks, and an audit trail naming who decided); static, non-expiring tokens rotated by redeploying (a real deployment has an OAuth 2.1 authorization server issuing short-lived Agent tokens, with overlap and revocation); a static bearer for `/mcp`, so OAuth-only MCP hosts cannot connect (a real deployment puts that authorization server, `workers-oauth-provider`, in front of `/mcp`). From 11: the Agent token is public, committed to the repo and shown in the README, so anyone can create, revise and submit Drafts, while nothing is sent without the never-committed Reviewer token (a real deployment issues per-Agent credentials through an authorization server, never in source control); a single production environment with manual `terraform apply` and `wrangler deploy` (a real deployment adds staging and CI-driven deploys with reviewed migrations). From 13, extending that entry: tests run only locally through `pnpm validate`, with no CI and no Git hooks (a real deployment runs unit, integration and e2e tests in CI on every change, gates deploys on them, and runs the live Resend contract test on a schedule). From retention (decided at map level after 13): no retention policy, so Drafts, Revisions, verdicts and Revision bodies are kept forever, unsent Drafts stay open indefinitely (there is no Discard), and an R2 body orphaned by a failed Revision commit is never removed (a real deployment has a retention policy, for example purging bodies of Drafts that are `SENT`, `FAILED` or long inactive after a fixed period while keeping the verdict record, plus a periodic sweep of R2 bodies without a Revision row). Known limitation to state alongside: CLI and MCP list reads may be briefly stale (no D1 bookmark kept between calls).
- The spec must contain a **"Future increments"** section (first entry: HTML body). Further entries so far: discarding a Draft; delivery tracking (delivered, bounced, complained) via Resend webhooks or `GET /emails/{id}`, which also resolves `OUTCOME_UNKNOWN` Sends via the `draft_id` tag; persisting the D1 bookmark in the CLI and MCP session; per-Draft Durable Objects (send-topology option B) if write locality or throughput ever matter; a diff between the Revision the Reviewer had loaded and the current one after a superseded verdict; per-verdict passkey confirmation (WebAuthn user verification); notifying the Reviewer when a Draft becomes Pending; an MCP App review view with its own Reviewer login that calls the API directly with a Reviewer token; from 09: large bodies and attachments through a dedicated upload endpoint (or presigned R2 URLs) rather than streaming the Draft request; from 10: OAuth 2.1 for `/mcp` via `workers-oauth-provider`, so OAuth-only MCP hosts can connect; from retention: a retention policy with a sweep of orphaned R2 bodies (together with discarding a Draft).
- Convention: enum values are upper snake case (`NOT_SENT`, `PENDING`).
- Testing: Vitest and Playwright. Priority 1 integration tests, priority 2 e2e tests, priority 3 unit tests.
- Prerequisite for building, not a ticket: a Cloudflare account and a Resend account with a verified sending domain or the sandbox address. The Resend team serves this system alone, since its rate limit (10 requests per second) is per team.
- Tracker: local markdown (this folder). No git. Research findings go to `research/<name>.md`, linked from the ticket.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [Resend send semantics](issues/01-resend-send-semantics.md): `Idempotency-Key` dedupes the same method+endpoint+body for only 24 h (`409` on a different body, or while the first request is in flight). The response carries only the email ID, there is no lookup by key, and the SDK neither throws nor retries. Status comes from `GET /emails/{id}` `last_event` or from Svix-signed, at-least-once webhooks.
- [MCP on Cloudflare and MCP Apps](issues/04-mcp-on-cloudflare-and-mcp-apps.md): stateless `createMcpHandler` (SDK v2, Streamable HTTP, no DO) behind `workers-oauth-provider`; MCP Apps is stable with app-only tools, but the server cannot tell a UI click from an agent call, so verdicts need a separately authenticated Reviewer channel
- [How cup is built](issues/02-cup-architecture.md): pnpm+Turbo monorepo; code-first `@hono/zod-openapi` contract packages (`*-api.routes`) with exported OpenAPI JSON, Hono RPC `hc` clients wrapped in hand-written classes (`*-api.client`), a commander CLI on the client, one Wrangler-deployed Worker; cup has no MCP server
- [Draft lifecycle and states](issues/05-draft-lifecycle.md): Revision data is immutable but its review status is mutable (`UNSUBMITTED`/`PENDING`/`APPROVED`/`REJECTED`/`SUPERSEDED`); the Draft mirrors its latest Revision; Submission is explicit and once per Revision; revising supersedes a pending Submission; the Approval triggers the Send automatically (nobody has a send operation); sending status `NOT_SENT`→`QUEUED`→`SENT`|`FAILED`, `FAILED` terminal (recover with a new Draft); no Discard; SQL `CHECK`s guard allowed combinations
- [Cloudflare primitives for exactly-once and concurrency](issues/03-cloudflare-concurrency-primitives.md): nothing on Cloudflare sends exactly once (Queues, DO alarms and Workflow steps are at-least-once; Workers don't retry); use a durable per-Draft claim (DO synchronous SQLite with output gates, or a D1 conditional UPDATE on the primary) plus an at-least-once driver, and close the crash window with a Resend idempotency key derived from the Draft
- [Binding an approval to the reviewed Revision](issues/06-approval-binding.md): a verdict names Draft id + Revision id and succeeds only on the latest `PENDING` Revision (one conditional UPDATE; immutability makes hashes/ETags unnecessary); distinct 409s `REVISION_SUPERSEDED`, `REVISION_ALREADY_DECIDED` (with `existingVerdict`, also for a repeated identical verdict), `REVISION_NOT_SUBMITTED`, `DRAFT_APPROVED`; the UI always shows them and offers an explicit reload, never carrying a verdict over; first commit wins revise-vs-verdict races; `approvedRevisionId` is written with the Approval and the Send reads only it; the Approval covers recipients and content, not `from`
- [Sending exactly once](issues/07-exactly-once-sending.md): option C of [send-topology-options](research/send-topology-options.md): D1 is the single source of truth with outbox columns, Revision bodies in R2; the Approval `batch()` freezes key `draft-send/<draftId>`, `outgoingEmail` (`from` resolved then, `draft_id` tag) and `deadline = approvedAt + 23 h`, then enqueues inline; one paced Queue consumer (concurrency 1, batch 8, ≥ 1 s) is the only Resend caller and only retry clock (backoff from 1 s, doubling, capped at 1 h, at least `Retry-After`); a bounded Send reconciler cron re-enqueues lost hand-offs and fails Sends stuck past the deadline; `FAILED` carries `REJECTED_BY_RESEND` or `OUTCOME_UNKNOWN`, and a late `SENT` overrides `FAILED`; no Resend call after the deadline; lists read D1 replicas with bookmark read-your-writes
- [The Reviewer's surface](issues/08-reviewer-surface.md): the Review UI, a deployed React SPA in cup's black-and-white style, is the only human interface and the only verdict channel (no MCP App, Reviewer CLI, elicitation or notifications in v1); it shows Pending and Decided lists; "accessible" means reachable without setup, no WCAG level; credential-boundary threat model (co-located Agents are a Demo simplification); Draft responses carry a `reviewUrl`; no CLI has verdict commands
- [API resources and operations](issues/09-api-surface.md): one API and one `@hono/zod-openapi` contract with a per-route version segment (`/api/v1/drafts…`); its OpenAPI 3.1 document is the published contract at `GET /api/openapi.json` (snapshot-tested); every route takes Agent and Reviewer credentials except approval/rejection (Reviewer-only, 403 `REVIEWER_ONLY`, never in MCP or CLI); create, list, get, revise (requires `baseRevisionId`), submit, get Revision; a repeated Submission is now 409 `REVISION_ALREADY_SUBMITTED` (revises 05); prefixed UUIDv7 ids, omitted nulls, `body: { plainText }` as buffered JSON, limits 50 recipients / 998-char subject / 100 KB body; lists filter by `reviewStatus`/`sendingStatus` with `orderBy`/`order` and cursor paging; mutations return a body-less Draft summary; cup error envelope; `X-Read-Bookmark`; six hand-written MCP tools and a commander CLI `draft-approval`
- [Keeping Agent and Reviewer apart](issues/10-agent-reviewer-separation.md): two preconfigured 256-bit bearer tokens (`agent_…` shared by all Agents, `reviewer_…` for the Review UI) in Worker secrets `AGENT_TOKEN`/`REVIEWER_TOKEN`; the role comes only from which secret's digest matches (constant time), and a `requireReviewer` guard on approval/rejection returns 403 `REVIEWER_ONLY`; `/mcp` takes the Agent token as a static header, passes it through to the API, and answers the Reviewer token with 403 `AGENT_ONLY` (no OAuth in v1); the SPA has a token screen and keeps the token in `localStorage` (never in the bundle); no cookies, so no CSRF; SPA and API share one origin with no CORS, a strict CSP with `frame-ancestors 'none'`, and text-only rendering; CLI uses `RESEND_CHALLENGE_TOKEN` and falls back to the built-in production URL; fixed local tokens only under a local-env flag
- [Storage and app structure on Cloudflare](issues/11-cloudflare-app-structure.md): one Worker (`fetch` for `/api/*`, `/mcp` and the SPA under `/app` via `env.ASSETS` with security headers, `/` → `/app/`; `queue` for send Queue and DLQ; `scheduled` for the Send reconciler); `/mcp` calls the API through the typed client with an in-process `fetch` into the same Hono app; Drizzle on D1 with generated SQL migrations and one cast helper for D1 sessions; cup's package layout with `libs/email-drafts` owning storage and the Send pipeline; Terraform (state in R2) for D1, R2, Queues and the Resend domain, production only at `resend-challenge.patricktree.me`; both tokens are Worker secrets handed out of band (the Agent token was first public and committed as a var, and became a secret later); local tokens need `LOCAL_DEVELOPMENT` plus a local host; integration tests run the whole Worker locally with test-only `/__test/queue` routes and a `node:http` Resend stub; e2e is Docker Playwright against `wrangler dev`
- [Review UI](issues/12-review-ui.md): settled without a prototype, simplest options throughout: routes `/app/` (Pending), `/app/decided`, `/app/drafts/$draftId` under one header with Sign out; the token screen renders in place of the requested route, so deep links survive; plain tables with "Load more"; the Draft page shows recipients, subject, escaped `pre-wrap` body and an earlier Rejection reason; Approve and Reject (optional reason) with no confirmation dialog, disabled in flight; after a verdict the page stays and polls every 3 s while `QUEUED`; verdict errors show inline with "Reload Draft", never as toasts; cup look without its dialog, toast or input; global CSS ships as an emitted stylesheet, because cup's inline `<style>` injection breaks the CSP
- [Testing strategy](issues/13-testing-strategy.md): a fresh `createTestHarness` per test (empty D1/R2/Queue, ~0.2 s); races forced deterministically by a gated D1 double in `libs/email-drafts` (holds a chosen statement) plus a 10-way `Promise.all` HTTP smoke; a race catalogue (verdict‖verdict, verdict‖revise, revise‖revise, submit races, duplicate delivery, reconciler‖consumer, late `SENT`) where every loser leaves no partial write, so each statement in the Approval and revise batches carries its own guard; the Resend stub models idempotency (ledger by key, 409 invalid/concurrent) and "exactly once" = one ledger email per approved Draft; time via backdated rows through `getEnv().DB`, no clock abstraction; MCP via the SDK client into `worker.fetch`; CLI spawned against an API stub; e2e per-test `wrangler dev` with real Queue delivery, role locators, five desktop screenshot baselines, no axe; unit tests for pure functions only; opt-in live Resend contract test; no retries, no CI, no Git hooks
- [Observability](issues/14-observability.md): not asked for, so v1 builds none: no `observability` block in `wrangler.jsonc` (`wrangler tail` for debugging), no event logging, only a bare `console.error` with the root cause on error paths (failed enqueue, `invalid_idempotent_request`, DLQ, unhandled 5xx); `requestId` in error envelopes and D1 rows as the audit trail stay; no log assertions in tests; attempt count, last error and next attempt time are not recorded (revises 07); everything else is the "No observability or alerting" Demo simplifications entry
- [Spec assembly](issues/15-spec-assembly.md): [spec.md](spec.md) written and confirmed: standalone, 18 sections from Overview and Requirements coverage to Demo simplifications, Known limitations, Future increments and Sources, final decisions only; while assembling: `updatedAt` renamed `lastActionAt` (not touched by Send outcomes), 500 `INTERNAL_ERROR` plus `X-Request-Id`, `max_batch_timeout: 1` in production, unlisted Resend 4xx final and other statuses retryable, no caching anywhere, no per-request logging
