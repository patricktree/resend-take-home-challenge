# Cloudflare Worker

## Integration tests

- Integration tests run through the `useWorker()` fixture in `test/use-worker.ts`: one Worker per test, concurrent within a file, migrations applied, empty storage.
- Integration tests count Send Queue messages with `readSentSendQueueMessages(worker)`, or every `send()` and `sendBatch()` call with `readSendQueueCalls(worker)`: the test entry point `test/worker.ts` wraps `SEND_QUEUE` in a recording double before delegating to the production `fetch` and `scheduled`, and exposes the recording as an RPC method, not a route. `runCronTick(worker)` runs one tick of the Send reconciler through `worker.scheduled()`; tests backdate `approved_at`, `deadline` and `enqueued_at` through `worker.getEnv().DB` rather than faking the clock.
- Send pipeline tests (`send-pipeline.test.ts`, `send-reconciler.test.ts`, `send-dlq.test.ts` and `send-outcome-races.test.ts` in `test/`) send through a per-test Resend stub, usually set up with `useSendPipeline()` and `createApprovedDraft()` from `test/use-send-pipeline.ts`: `useResendStub()` in `test/use-resend-stub.ts` starts `@draft-approval/resend-stub` (`qa/resend-stub`, a `node:http` server that models Resend's idempotency and takes scripted answers, hangs and held requests), and `useWorker(context, resendStubWorkerOptions(resendStub.url))` points `RESEND_BASE_URL` at it with a dummy `RESEND_API_KEY`. Each scenario delivers its batch with `deliverSendQueueBatch(worker, messages)`, which calls the test-only route `POST /__test/queue` of `test/worker.ts` (the real `queue()` handler on a hand-built `MessageBatch`) and returns each message's ack, retry and `delaySeconds`; `deliverSendDlqBatch(worker, messages)` does the same for the DLQ consumer through `POST /__test/dlq`. Assert "exactly once" in every scenario with `expectExactlyOneEmailPerSentDraft(worker, resendStub)`. Only one test uses real Miniflare delivery (`useWorker(…, { shouldConsumeSendQueue: true })`, the `send-queue-delivery` environment of `test/wrangler.test.jsonc`); the default test environment has no Queue consumer, so nothing races the route.
- Build a fixture of dozens of Drafts with one D1 `batch()` of inserts, such as `insertDrafts()` in `test/lists.test.ts`; [`libs/drafts/AGENTS.md`](../../libs/drafts/AGENTS.md) explains why.
- The integration tests serve a small fixture instead of the built Review UI (`test/assets/`).
- [`libs/mcp-server/AGENTS.md`](../../libs/mcp-server/AGENTS.md) describes the MCP layout and its tests in `test/mcp.test.ts`.

## Wrangler configs and the dev server

- `wrangler.jsonc` is the production config and the one `pnpm dev` uses; `test/wrangler-config.test.ts` pins the settings the spec prescribes. Its resources come from `terraform/` ([`terraform/AGENTS.md`](../../terraform/AGENTS.md)). [`libs/drafts/AGENTS.md`](../../libs/drafts/AGENTS.md) covers the D1 migrations.
- In `pnpm dev`, `vite.config.ts` merges the Review UI's Vite config and bridges two dev-server gaps: it serves `/app/index.html` and allows inline scripts and styles in the CSP.
